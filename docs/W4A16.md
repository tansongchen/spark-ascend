# W4A16：压缩权重并融合 decode

W4A16 使用 INT4 权重和 BF16 激活，先减少权重数据量，再将 decode 的线性层和层内计算融合。本篇保留 `w4a16_v10b` 的设计与历史结果：完整模型约 **4.164542 ms/token（240.122 token/s）**，但**完整模型 logits 仍未通过预设数值门限**。

新增 `w4a16_reborn` 已实现约 **310.77 token/s**，它重新设计线性层与完整 attention 搬运，并额外量化 decode LM head 和私有 KV。其数据格式、精度变化与验证记录见[新版说明](W4A16_REBORN.md)。

构建、插件安装和模型运行见 [README](../README.md)。

## 量化与存储

从原 BF16 checkpoint 做对称 RTN，沿输入通道每 128 个权重为一组：

```text
scale = BF16(max(abs(weight)) / 7)
q = clamp(round(weight / scale), -7, 7)
反量化权重 = BF16(q × scale)
```

scale 保存为 BF16，并使用保存后的 scale 计算 q。36 层的 QKV、注意力输出、MLP gate/up/down 共 180 个矩阵量化；Embedding、共享 LM head、RMSNorm 和注意力 g_proj 保持 BF16。激活和 KV cache 也保持 BF16。gate/up 合并后，运行时共有 144 个量化线性层。

参数数据从 8,224,158,720 降至 2,620,830,720 字节，减少 **68.13%**。这不是整体 NPU 显存降幅，运行仍需 KV cache、工作区和框架内存。RTN 会引入量化误差，目前未做系统任务准确率评测。

本地 checkpoint 以 int32 保存 8 个有符号 INT4，权重形状 `[N/8,K]`，scale 形状 `[N,K/128]`。格式标记为 `spark_int4_signed_output_pack_v1`，需要本仓库插件，不可直接作为 AWQ/GPTQ/msModelSlim 产物加载。

重新导出时使用新目录：

```bash
python -B utils/quantize_spark_w4a16.py \
  --source /data1/t00995472/models/Spark-X2.5-4B \
  --output /data1/t00995472/models/Spark-X2.5-4B-W4A16-G128-new \
  --group-size 128
```

## 为什么还要融合

仅换成原生 `npu_weight_quant_batchmatmul`，权重变小并不保证整模型更快。原生 W4A16 eager 在既有 32K/4K 测试中约为 12.612 ms/token；profile 显示线性层设备耗时下降，但仍有较多算子派发和主机张量操作。这说明需要进一步检查执行路径，尚不能将全部时间差量化归因于主机开销。

融合版本沿用 BF16 融合层的同步、RoPE、KV cache、attention、残差和归一化流程，替换 QKV/O/gate-up/down 的权重读取与 GEMV。每 token 为 36 个融合层调用；prefill 仍走原生 W4A16，LM head 与采样保持原路径。

## v10b 的关键优化

CPU 先将 checkpoint 中的 INT4 重排为 GEMV tile，保留原 group scale，不再次量化。v10b 使用 `spark_w4a16_tile_g128_v1` 布局：压缩 INT4 加 scale，scale 在该布局中由 BF16 精确扩展为 FP32。

设备端直接使用 INT4→BF16 转换指令，每次一起处理两组权重，完成 BF16 乘法后显式提取两个 FP32 向量并累加。合并转换降低解码指令开销；权重在片上按需处理，不常驻完整 BF16 反量化矩阵。

早期“解包到 UB 再 GEMV”和查表方案用于定位瓶颈；最终 v10b 不使用查表。`decode_w4a16_lut_gemv.h` 保留历史名称，其中也包含 v10b 所需实现。高半字节提取曾出现布局错误，因此独立解包逐位检查是运行性能测试的前提。

## 性能结果与数值边界

2026-10-20，物理 NPU 4、Ascend 950PR、32768 输入 / 4096 输出、TP=PP=1、单请求、完整预热一次后连续测三次：

| 指标 | 第 1 次 | 第 2 次 | 第 3 次 | 均值 |
| --- | ---: | ---: | ---: | ---: |
| TPOT，ms/token | 4.162687 | 4.166550 | 4.164391 | **4.164542** |
| TTFT，ms | 1554.180 | 1570.449 | 1616.941 | 1580.523 |

每轮 4096 个自由生成 token 均与此前原生 W4A16 基线一致，21 个 decode 频率样本均为 1650 MHz；稀疏采样不证明全程恒频。240 token/s 目标仅有约 0.05% 余量，不宜外推到其他负载或机器。

正确性需要分开看：

- **INT4 实现检查**：三种 tile 共 94208 个值，重复三次解包逐位一致；单层 CPU 分阶段参考与保护区检查通过。
- **融合与原生 W4A16 的一致性**：128、1024、32768、36800 四种上下文共 252 个 decode 步，top-1 全一致，但最大 logits NRMSE 约 **14.01%**，超过预设 **2%** 门限，因此未通过。筛查同时要求 cosine≥0.999、top-1 一致率≥95%。
- **量化相对原 BF16 模型的质量**：以上两项都不能替代这项评估，目前没有系统准确率结论。

逐层诊断发现 RoPE 缓存和 attention 分块/舍入产生的差异会向后传播，并在部分 MLP 层放大；局部 Q/K/V 修正不足以解决整模型超限。尚未确定完整误差归因，后续应以真实输入捕获及同前缀 logits 对照验证，不把 top-1 一致或短请求通过视为完整数值验收。

## 验证工具与证据

激活环境、确认设备空闲后，从仓库根目录执行；变量沿用 README 示例：

```bash
# 独立解包 + 完整单层 CPU 参考
python -B utils/validate_w4a16_kernel.py --npu 2 \
  --build "$SPARK_BUILD/w4a16" --layer 3 --length 32768 \
  --output "$SPARK_RESULTS/w4a16-kernel.json"

# 四种上下文的原生/融合同前缀 logits；当前版本预期会报告超限
python -B utils/validate_w4a16_model.py --npu 2 \
  --library "$SPARK_BUILD/w4a16/libdecode_layer_w4a16.so" \
  --output "$SPARK_RESULTS/w4a16-logits"
```

第二个脚本在未通过门限时返回非零，不能把它记作验收通过。`utils/analyze_w4a16_qkv.py`、`utils/analyze_w4a16_mlp.py`、`utils/analyze_w4a16_attention.py` 可分析捕获的层间数据；所需采集参数见 `utils/validate_w4a16_model.py --help`。

原始证据在 `/data1/t00995472/spark-w4a16/fused/v10b-compact-convert/`：`bench-32k/analysis.json` 保存性能审计，`model-validation-qkv/result.json` 保存 logits 结果。量化导出报告位于 checkpoint 内的 `quantization_report.json`。
